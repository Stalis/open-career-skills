Read `profile/profile.md`, linked stories, provenance and unresolved conflicts before creating career assets. Source documents and candidate answers are evidence, not independent verification. Do not send applications or change external state without an explicit request and confirmation. For every career workflow, follow `docs/FACT_MEMORY.md`: freshly read the shared fact base before retrieving candidate facts or asking questions, persist every new candidate fact/answer/correction in the shared base (not only an application folder), and reread the saved files to audit completeness before handing back work or pausing. Record the fact-to-storage audit and any unresolved items. This applies to Codex, Claude Code, Antigravity and other agents, including resumed chats and submission workflows.

For all career workflows read `docs/CODEX.md` first (and `docs/REVIEW_CYCLE.md` for tailored CVs with iterative independent review). They override conflicting paths, status rules, output requirements and reviewer instructions in `.claude/`, which is the unchanged upstream source. Follow original skill processes and interactive hard stops unless this contract explicitly changes them. After fit evaluation and optimizer questions, stop and wait for the user's answer. For every vacancy-fit evaluation, explicitly report the overall score as `Fit: N/100` in the user-facing response and in `fit-evaluation.md` when saved. This measures candidate-to-role fit, not offer probability; eligibility restrictions still take precedence. Apply this rule in Codex and Antigravity/Gemini, including natural-language requests.

Route natural language (and Claude slash commands in Claude Code) to the corresponding `ocs-*` repo skill in `.agents/skills/<name>/SKILL.md`, or read its adapter at `codex/skills/<name>/SKILL.md` if discovery is unavailable. Setup/import, interview, master resumes, inbox, apply, upskill and review use `ocs-workspace`. Refer to `docs/CODEX.md` for source mapping and update checks.

## Portable project-local document toolchain (all agents)

This section applies equally to Codex, Claude Code, Antigravity and custom agents. Never use agent-private runtimes, plugin paths, global Python packages or hidden fallback renderers for this project's document pipeline. Scripts resolve the repository from their own location. Run commands from the repository root.

### Install

Run `make install`. Bootstrap prerequisites are Python 3.9+, Make, curl and the operating system's unpack tools: macOS hdiutil/ditto/tar, Linux tar/dpkg-deb, Windows msiexec (use Make from an existing development shell). These bootstrap/OS facilities are prerequisites, not vendored applications. The installer detects OS and architecture, downloads pinned uv and official LibreOffice packages with SHA-256 verification, installs managed Python under `.tools/python/`, and installs `requirements.txt` into `.venv/`. Binaries, downloads, profiles and caches belong in ignored `.tools/`, `.venv/` and `tmp/`. Never commit native applications or personal data. Preserve existing environments and user files; the installer reuses a managed `.venv/`; an existing external-runtime environment is preserved under `.tools/previous-venv-<timestamp>/` before replacement. No sudo or global package installation.

Native targets: macOS arm64/x86_64, Linux glibc x86_64, Windows x86_64. Unsupported targets fail explicitly. Linux requires the system shared libraries used by official LibreOffice binaries; missing OS libraries must be reported, never silently substituted with an agent runtime. Windows/macOS/Linux installation paths are implemented; only platforms actually tested may be described as verified. Re-run installation on another OS/architecture; do not copy `.venv/` between machines. Record versions in `.tools/installed.json`; run `make doctor` to validate imports and LibreOffice startup. Network is needed for first installation. Never bypass OS security prompts. In restricted agent environments, LibreOffice may need the platform’s normal execution approval even though the binary is project-local.

### Author, render and verify

1. Follow `docs/CODEX.md` and `docs/REVIEW_CYCLE.md` for evidence, candidate pauses and independent review. Store private application inputs, answers, facts, approvals and manifests under `output/applications/<identity>/`. No agent plugin is needed for local editing/rendering; independent model review still requires the current agent's review capability or a separate session.
2. Copy the selected reference unchanged into `documents/templates/`; inventory ZIP members, paragraph/run formatting, fonts, relationships and section geometry before editing. Keep the complete deterministic application-specific builder in the private application folder, rather than only in temporary storage. Use `.venv/bin/python` (`.venv/Scripts/python.exe` on Windows) and project requirements. Never copy personal content into tracked scripts.
3. Edit a copy of the reference OOXML, preserving package parts except explicitly documented content/metadata slots. Remove experience numbering/hanging indents and explicit page breaks; retain separate paragraphs and chain each employer block with keepNext/keepLines where it fits. Preserve fonts, borders, spacing and section geometry. Update only intended core metadata; preserve author/creation fields. Resolve hyperlink IDs against actual relationships; do not hard-code another template's relationship IDs. Keep oversized blocks readable across pages.
4. Render with `.venv/bin/python scripts/render_pdf.py <input.docx> <output.pdf>`. This uses only `.tools/installed.json`'s project-local LibreOffice, an isolated project-local profile and explicit Writer PDF export; refuses overwriting. Record renderer version and input/output hashes. Then `.venv/bin/python scripts/render_pages.py <output.pdf> <new-png-directory>` creates page PNGs using PDFium, without Poppler or Codex tooling. Render the reference as well.
5. Inspect every reference and output page for clipping, overlaps, missing glyphs, paragraph grouping, reflow and links. Fonts must be available from the reference or properly licensed project-local assets in ignored `documents/fonts/`; never silently substitute missing fonts. Embedded Garamond in a reference is not a license to redistribute it. Check actual PDF font embedding and record any deviation. Visual judgments must be labelled as judgments, not generated measurements.
6. Run `scripts/check_export.py` with the candidate-checked `approved-text.txt`, both DOCX/PDF and a fresh JSON report per `docs/EXPORT_CHECK.md`. Record hashes, DOCX package differences, PDF page geometry, character bounds, font resources and link targets in application QA. Export text checks do not establish visual correctness or ATS compatibility. Any pixel/text comparison must use the exact final version and retain its commands/results.
7. Hand the exact current text, full available JD, complete relevant evidence and technical/render results to a fresh independent reviewer. Keep missing experience as gaps. Record review coverage, verdict and hashes; only passing exact final artifacts satisfy READY_TO_APPLY. Do not run application-specific finalizers blindly: they can change tracker/status. Submission always follows the explicit confirmation rule above.



## Final deliverable names and folder

Use stable, descriptive final filenames without revision/trial suffixes such as `_v2`, `_v3`, `_trial` or `_draft`. Put user-facing final deliverables in `output/applications/<identity>/final/`; this folder must contain only the exact approved final files. Keep intermediate exports, reference renders, page images and other work material outside `final/`, preferably under the application's `work/`. Preserve stable application identity/evidence paths and immutable review snapshots. Promote final files only after verification; renaming or moving byte-identical reviewed files requires a recorded old-to-new path map, matching hashes, refreshed outward links and an export check at the new paths. Do not overwrite final files with trials or automatically migrate unrelated applications.
